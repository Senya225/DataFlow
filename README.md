DataFlow — библиотека хранения и обработки однотипных данных
DataFlow — переиспользуемая библиотека на C# для хранения, фильтрации, преобразования и извлечения однотипных данных без дублирования кода под каждый тип.

Проект выполнен в рамках объемного контрольного задания по темам КТ №27 – КТ №30: обобщения в C# (иерархии обобщённых классов, обобщённые структуры и делегаты, обобщённые интерфейсы, методы расширения).

1. Описание библиотеки
DataFlow — это небольшая переиспользуемая библиотека, которая позволяет хранить и обрабатывать однотипные данные с помощью обобщённых классов, структур, делегатов, интерфейсов и методов расширения, не дублируя реализацию под каждый конкретный тип.

Проект состоит из двух проектов решения:

DataFlow.Core — библиотека классов: обобщённые классы, структура, делегат, интерфейсы, методы расширения. Не содержит предметных типов и ничего не знает о предметной области.

DataFlow.Demo — консольное приложение: конкретные типы предметной области и сценарий, который использует ядро так, чтобы были видны все возможности библиотеки.

2. Предметная область и типы домена
Выбранная область: складской учёт.

Типы домена (DataFlow.Demo/Domain.cs)

Как Product реализует IEntity: через свойство int Id { get; set; } — именно по нему InMemoryRepository<T> ищет элемент.

Как Product реализует IComparable<Product>: сравнение по Price, чтобы FindMax мог выбрать самый дорогой товар.

csharp
public sealed class Product : IEntity, IComparable<Product>
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public decimal Price { get; set; }

    public int CompareTo(Product? other)
    {
        if (other is null) return 1;
        return Price.CompareTo(other.Price);
    }

    public override string ToString() => $"{Name} ({Price:0.00})";
}

public sealed class Customer : IEntity
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public string City { get; set; } = "";
}

public abstract class Animal
{
    public string Name { get; set; } = "";
    public override string ToString() => $"{GetType().Name} по имени {Name}";
}

public sealed class Dog : Animal { }
Customer реализует только IEntity — это показывает, что IComparable подключается выборочно, а не обязателен для всех типов домена.
Где параметр типа фиксируется, а где остаётся открытым:

LabeledBuffer : Buffer<string> — параметр типа фиксирован (string), класс не обобщённый.

GuardedBuffer<T> : Buffer<T> — параметр типа открыт, класс остаётся обобщённым.

Container<T> и InMemoryRepository<T> — открыты на уровне класса, но InMemoryRepository<T> имеет ограничение where T : IEntity.

4. Разбор по шагам (ответы на вопросы)
Шаг 0. Подготовка решения
Зачем в решении два проекта, а не один? Разделение ядра и демонстрации доказывает переиспользуемость: ядро не знает ничего о предметной области и может быть подключено к любому другому приложению. Если бы всё лежало в одном проекте, библиотека неизбежно «приросла» бы предметными типами.

Что произойдёт, если убрать dotnet add reference? Демонстрация не увидит типы ядра: компилятор выдаст ошибку «не найден Buffer» и т.п. Ссылка между проектами связывает их на этапе компиляции.

Почему проект библиотеки нельзя запустить, а консольный — можно? У classlib нет точки входа (Main). У console она есть, поэтому dotnet run запускает именно её.

Шаг 1. Обобщённый базовый класс Buffer<T>
Чем protected отличается от private и public именно для этого поля? private сделал бы поле невидимым для наследников, и LabeledBuffer не смог бы его использовать. public нарушил бы инкапсуляцию: внешний код мог бы менять список в обход TryAdd. protected — компромисс: поле видно наследникам, но не снаружи.

Что означает readonly для поля — и запрещает ли оно добавлять элементы? Запрещает переприсваивать саму ссылку (items = new List<T>() после конструктора). Но не запрещает вызывать items.Add(...) — содержимое списка меняется.

Зачем TryAdd возвращает bool, если сейчас всегда true? Это контракт для наследников: базовый класс объявляет «здесь возможен отказ», а GuardedBuffer<T> этот отказ реализует. Без bool наследнику пришлось бы бросать исключения или менять сигнатуру.

Что произойдёт, если убрать virtual? GuardedBuffer<T> не сможет переопределить TryAdd — компилятор выдаст ошибку CS0506 «нет подходящего метода для переопределения».

Чем new() отличается от new List<T>()? new() — целевой типизированный new: тип выводится из контекста (поля List<T>). Полностью эквивалентно new List<T>(), но короче.

Шаг 2. Наследование с фиксацией типа — LabeledBuffer
Чем LabeledBuffer : Buffer<string> отличается от GuardedBuffer<T> : Buffer<T> — и почему это разные стратегии? Первое — фиксация: тип известен заранее, класс перестаёт быть обобщённым. Второе — сохранение обобщённости: класс работает с любым T, но расширяет поведение.

Почему PrintAllUpper() невозможно было написать в Buffer<T>? Компилятор не знает, что такое T, поэтому не может гарантировать наличие метода ToUpper(). Внутри LabeledBuffer тип зафиксирован как string, и метод существует.

Что случится, если попытаться объявить LabeledBuffer<int>? Ошибка компиляции: LabeledBuffer не обобщённый, у него нет параметров типа. Он уже наследует Buffer<string>.

Смог ли бы LabeledBuffer хранить числа, если бы наследовался от Buffer<object>? Технически да, но теряется типовая безопасность: в Buffer<object> можно положить и string, и int, и всё что угодно. При извлечении потребуется приведение типов, и ошибки перейдут из компайл-тайма в рантайм.

Шаг 3. Переопределение с сохранением обобщённости — GuardedBuffer<T>
Почему проверка отказа стоит до вызова базового метода, а не после? Отклонённый элемент вообще не должен попасть в список. Если сначала добавить, а потом отклонить, придётся удалять его обратно — лишняя логика и потенциальные ошибки.

Что произойдёт, если считать AcceptedCount до проверки результата базы? Счётчик начнёт расти и для отклонённых элементов — он перестанет отражать фактическое число принятых.

Чем отличается поведение GuardedBuffer<int> и GuardedBuffer<string>, если код класса один и тот же? Только правилом, переданным в конструктор (x => x > 0 vs s => !string.IsNullOrWhiteSpace(s)), и типом элементов. Поведение задаётся снаружи — это и есть универсальность.

Почему нельзя вместо base.TryAdd(item) написать items.Add(item), если результат будет тот же? Теряется переиспользование базовой логики: если Buffer<T> изменит правила (например, добавит проверку на null), GuardedBuffer их не унаследует. Задание проверяет именно вызов base.

Что произойдёт, если перенести условие отказа внутрь тела класса вместо параметра конструктора? Класс перестанет быть универсальным: для каждого нового правила пришлось бы писать новый класс. Передача Func<T,bool> через конструктор делает правило параметром, а не частью кода.

Шаг 4. Record<T>, делегат Mapper и обобщённый Map
Чем struct отличается от class для вызывающего кода? struct — значимый тип: копируется при передаче, не может быть null (без Nullable<T>). class — ссылочный: передаётся ссылка, может быть null.

Что выведет Console.WriteLine(record), если не переопределять ToString()? DataFlow.Core.Record1[System.Double]— имя типа вместе с обобщённым аргументом. ПереопределениеToString()даёт читаемый вывод°C: 20`.

Как компилятор понял, что TResult равен string во втором вызове? По типу возвращаемого значения лямбды: (double c) => c >= 15 ? "тепло" : "холодно" возвращает string. Компилятор выводит T = double, TResult = string из аргументов и сигнатуры делегата.

Почему нельзя было реализовать преобразование отдельными методами ToFahrenheit и ToCategory без обобщения? Пришлось бы писать отдельный метод на каждое преобразование — дублирование. Один Map<T,TResult> работает с любой парой типов и любой лямбдой.

Что произойдёт, если убрать переопределение ToString() — увидит ли это проверяющий в выводе программы? Да: в выводе вместо °C: 20 появится DataFlow.Core.Record1[System.Double]`. Это очевидно при сравнении с эталоном.

Шаг 5. Обобщённые интерфейсы и ограничение типа
Что произойдёт, если убрать where T : IEntity и попытаться написать тело методов? Внутри InMemoryRepository<T> нельзя будет обращаться к item.Id — компилятор не знает, что у T есть Id. Ограничение делает это свойство гарантированным.

Почему ограничение проверяется компилятором, а не во время выполнения? Это статическая проверка: тип подставляется на этапе компиляции, и компилятор знает, реализует ли он IEntity. Ошибки ловятся до запуска — это дешевле.

Что означает T? в GetById и почему это не то же самое, что Nullable<T> для значимых типов? T? для ссылочных типов — это аннотация «может быть null», а для значимых — Nullable<T> (то есть int? = Nullable<int>). В обобщённом контексте T? работает для обоих, но означает разное.

Что произойдёт, если добавить в IContainer<out T> метод void Put(T item)? Ошибка CS1961: out T требует использовать T только в возвращаемой позиции. Put(T) принимает T — нарушение ковариантности.

Шаг 6. Реализация репозитория на основе списка
Почему ограничение where T : IEntity нужно указывать и на интерфейсе, и на реализации? На интерфейсе оно задаёт контракт, на реализации — гарантирует компилятору, что внутри класса T действительно имеет Id. Без него реализация не скомпилируется.

Что означает return default; для ссылочного типа и для int? Для ссылочного — null. Для int — 0. Это разные значения, и в выводе это видно.

Что будет, если вернуть null при возможном типе-структуре? Какой код ошибки выдаёт компилятор? Ошибка CS0403 (или CS0266 в зависимости от контекста): null нельзя преобразовать в T, который может быть структурой. Нужен default(T) или T?.

Почему поле items здесь private, а в Buffer<T> было protected? У InMemoryRepository<T> нет наследников, которым нужен доступ к items, поэтому private — минимально необходимый уровень. В Buffer<T> наследники (LabeledBuffer) обращаются к items, поэтому protected.

Шаг 7. Ковариантность: класс против интерфейса
Почему IContainer<Animal> принимает Container<Dog>, а Container<Animal> — нет? IContainer<out T> объявлен ковариантным: T только на выходе, поэтому Dog можно безопасно выдать как Animal. У класса Container<T> такой гарантии нет — он инвариантен по умолчанию.

Какую цену мы заплатили, объявив out T? Нельзя добавлять методы, принимающие T (например, Put(T)). Ковариантность и «вход» параметра типа несовместимы.

Зачем класс помечен sealed, если ковариантность объявлена на интерфейсе? Чтобы наследник не мог добавить метод, принимающий T, и не сломал гарантию ковариантности. sealed защищает контракт out T от расширения, которое нарушило бы безопасность.

Приведите пример, где IContainer<Animal> дал бы больше пользы, чем Container<Animal>. Если функция принимает IContainer<Animal>, в неё можно передать и Container<Dog>, и Container<Cat>, и Container<Animal>. С Container<Animal> — только последний.

Шаг 8. Методы расширения
Что произойдёт, если заменить параметр IEnumerable<T> на List<T>? Что именно перестанет работать? Метод перестанет работать с массивами, IQueryable, результатами Where, словарями и т.д. — только с List<T>. Гибкость теряется.

Зачем в FindMax ограничение where T : IComparable<T> — что именно не скомпилируется без него? Без него внутри нельзя вызвать item.CompareTo(...) — компилятор не знает, что у T есть этот метод.

Почему метод нельзя заменить на готовый Max() из LINQ? Max() бросает InvalidOperationException на пустой последовательности, а по заданию FindMax должен возвращать default(T) без исключения.

Чем return default отличается от return null в вашем случае и почему это видно по выводу? default для int — это 0, для string — null. return null не скомпилируется для T = int. В выводе видно и null (пустой List<string>), и 0 (пустой List<int>).

Что означает best! и почему без него не собирается? Оператор «забытой проверки на null»: говорит компилятору, что best точно не null. Внутри цикла это гарантировано флагом found. Без ! компилятор выдаст предупреждение о возможном null.

Шаг 9. Предметная область и IComparable
Что произойдёт, если удалить Id из Product? Product перестанет реализовывать IEntity, и InMemoryRepository<Product> не скомпилируется (ограничение where T : IEntity).

Зачем CompareTo принимает Product?, а не просто Product? Интерфейс IComparable<T> объявляет CompareTo(T? other). Параметр может быть null, и метод должен корректно это обрабатывать.

Что будет, если CompareTo будет возвращать 1 всегда? Нарушается контракт: для равных элементов нужно возвращать 0. FindMax и сортировки начнут работать непредсказуемо — результат зависит от порядка элементов.

Как изменится вывод PrintAll, если убрать переопределение ToString()? Вместо Товар: Яблоко (120,00) выведется Товар: DataFlow.Demo.Product.

Почему Customer не реализует IComparable, а Product реализует? Customer не участвует в FindMax, поэтому сравнение не нужно. IComparable подключается только там, где есть смысл сравнивать элементы.

Шаг 10. Единый сценарий
Почему OutputEncoding выставлен первой строкой, а не где-то позже? Без неё кириллица в Windows-консоли превращается в «кракозябры», и весь вывод становится нечитаемым. Настройка должна быть до первого WriteLine.

Что в этом выводе доказывает, что GuardedBuffer<T> универсален, а не работает со строкой случайно? Два экземпляра с разными T (int и string) и разными правилами (x > 0 и !string.IsNullOrWhiteSpace(s)). Код класса один, но поведение разное.

По какой строке вывода видно, что счётчики экземпляров независимы? Счётчики независимы: numbers.AcceptedCount = 2 — при том что words.AcceptedCount = 1. Два экземпляра, два разных счётчика.

Найдите в выводе строку, где тип значения Record изменился с double на string. Как это связано с одной сигнатурой метода? Строка double → string: Категория: тепло — один метод Map, но TResult выведен как string по лямбде.

Что покажут строки про пустой List<int> и почему это не ошибка? FindMax на пустом List<int> = 0 — это default(int), а не ошибка. Отсутствие исключения — часть контракта.

Шаг 11. Три ожидаемые ошибки компиляции
Почему ошибка 1 возникает для класса, но не возникает для интерфейса? Класс инвариантен по умолчанию: Container<Dog> и Container<Animal> — разные типы. Интерфейс IContainer<out T> объявлен ковариантным, и преобразование разрешено.

Что изменится в ошибке 2, если заменить out T на in T? Ошибка исчезнет для Put(T) (это вход), но появится для GetItem() (это выход). in T требует использовать T только в принимаемой позиции.

Какие ещё типы нельзя подставить в InMemoryRepository<T> и почему? Любые типы, не реализующие IEntity: string, int, double, object, пользовательские классы без IEntity. Ограничение требует неявного преобразования к IEntity.

Почему компилятор ловит все три ситуации до запуска программы? Это статические проверки типов на этапе компиляции. Компилятор знает все типы и ограничения до выполнения.

Что означает принцип «проверка на этапе компиляции» для цены ошибки в разработке? Ошибка ловится до запуска, стоит дешевле, не доходит до пользователя, не требует тестов на этот случай.

6. Три ожидаемые ошибки компиляции
Файл DataFlow.Demo/ExpectedErrors.cs — все фрагменты закомментированы, чтобы проект собирался. Раскомментируйте по одному и снимите скриншот сообщения компилятора.

Ошибка 1 — инвариантность обобщённого класса (CS0029)
csharp
// Container<Animal> box = new Container<Dog>(new Dog { Name = "Шарик" });
Сообщение компилятора:
CS0029: Не удается неявно преобразовать тип "Container<Dog>" в "Container<Animal>".

Объяснение: Обобщённый класс инвариантен. Для компилятора Container<Dog> и Container<Animal> — разные типы, и он не может доказать, что подстановка безопасна. Та же ситуация через интерфейс проходит — потому что IContainer объявлен ковариантным (out T).

Ошибка 2 — нарушение ковариантности (CS1961)
csharp
// public interface IProbeContainer<out T>
// {
//     T GetItem();
//     void Put(T item);
// }
Сообщение компилятора:
CS1961: Недопустимое отклонение: Параметр типа "T" должен быть контравариантно допустимым на "IProbeContainer<T>.Put(T)". "T" является ковариантным.

Объяснение: Объявление out T — это обещание: параметр типа будет использоваться только на выходе. Метод Put(T item) принимает T на входе и обещание нарушает. Контравариантность in T существует именно для этого случая, но тогда T нельзя будет возвращать.

Ошибка 3 — нарушение ограничения типа (CS0311)
csharp
// var repo = new InMemoryRepository<string>();
Сообщение компилятора:
CS0311: Тип "string" не может быть использован как параметр типа "T" в универсальном типе или методе "InMemoryRepository<T>". Нет преобразования неявной ссылки из "string" в "IEntity".

Объяснение: Ограничение where T : IEntity требует, чтобы T реализовывал IEntity. У string такого интерфейса нет, и компилятор отказывается подставлять его в параметр типа.

7. Что осталось нереализованным и что сделал бы иначе
Что осталось нереализованным:

Нет удаления и обновления элементов в InMemoryRepository<T> — только Add и GetById по контракту.

Нет потокобезопасности: List<T> не защищён от конкурентного доступа.

Нет сохранения состояния между запусками (in-memory only).

Что сделал бы иначе при второй попытке:

Добавил бы IReadOnlyList<T> как возвращаемое значение для просмотра всех элементов вместо GetById-only.

Вынес бы правило допуска в GuardedBuffer<T> в отдельный интерфейс IPredicate<T>, а не в Func<T,bool> — читаемость выше.

Ввёл бы юнит-тесты (xUnit) на каждый шаг, а не полагался только на ручной вывод.

В FindMax добавил бы перегрузку с явным значением по умолчанию (FindMax<T>(source, T defaultValue)), чтобы можно было отличить «пусто» от «нашли default».
